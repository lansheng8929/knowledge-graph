## 真实端到端调试修复的 Bug（2026-08-07 晚）

- **Bug1 自死锁（严重）**：`PostgresTaskQueue.acquire()` 里 `SELECT ... FOR UPDATE` 锁住任务行后**未 commit**，保持连接持锁；handler 内 `store.set_stage()` 用**另一连接** UPDATE 同一行 → 被自己的行锁阻塞 → 行锁要等 `release()` 才释放 → 自己等自己，worker 永久卡死（任务一直 queued）。**修复**：acquire 的 `UPDATE status='running'` 后 `conn.commit()`（释放行锁、状态可见；advisory lock 是会话级，commit 不清除，仍由 `_lease_conn` 保持到 handler 完成）。
- **Bug2 response_model 过滤**：compute/recompute-intimacy 路由声明 `response_model=m.IntimacyResult`，FastAPI 把 `{success,data}` 过滤成 `{intimacies,stats}`，writer `resp.json()["data"]` 取不到 → KeyError 'data'。**修复**：移除这两个路由的 response_model（保持项目统一的 {success,data} 包装风格）。
- **顺带健壮性**：`TaskQueue._run` 的 `acquire()` 之前不在 try 内，异常会杀死 worker 线程；改为 try/except 记录后重试。

## 关键决策

- **亲密度不含边数（v2）**：v1 按对级别边数算导致同对边全同 + 数量双重计算（亲密度算一次、物理引擎叠加算一次）。v2 改为单条边质量，数量交给前端叠加；`frequency` 维度保留但默认关。
- **亲密度可更新**：新增 recompute 接口（全库/按类型/按边/按节点对），配置变更或时间流逝后触发重算刷新 `r.intimacy`。
- **不引入 Celery/Redis**：基础设施无 broker；用 Postgres advisory lock 实现全局串行，Memory 用标准库队列。
- **file-import-service 不自连 Neo4j**：亲密度计算复用 graph-ingestion 的 driver，通过 HTTP 只读接口暴露成服务（保持"唯一写通道"约束）。
- 当前主任务 = 两个子任务 [parse, compute_intimacy]；未来调整子任务入参/顺序只需改注册表与 DEFAULT_STEPS。
- B 子任务先全库计算亲密度（写库前查询统计），再随 ingest_links 把 intimacy 写入边 props（graph-ingestion `SET r += props` 展开为关系属性，查询端 `rel.get("intimacy",0.5)` 兜底）。
- 亲密度算法默认 count：`intimacy = 1 - 1/(1+total)`，total = 全库已有关系数 + 本批同对边数（无向合并）。
